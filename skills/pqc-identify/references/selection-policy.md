# 기존 암호 기능의 PQC 전환 기준

버전 2.5 · 2026-11-07. 판정 단위는 **기존 암호가 수행하는 업무 기능과 그 호출·키 흐름**이다. 전환할 기능과 유지할 보안 성질에서 시작해 **공식 표로 후보를 좁히고 알고리즘·정확한 매개변수·카테고리와 선택 이유까지 결정**한다. 기능 분류나 후보 나열만으로 선정 완료라고 하지 않는다. 요구가 없으면 카테고리 3으로 시작하거나 루트 키라는 이유로 5를 부여하는 규칙은 사용하지 않는다.

선정 책임은 에이전트에 있다. 공식 명세·프로토콜·대상 코드·구현 지원을 조사해 적용 범위에 사용할 집합을 결정하고 사용자에게 알고리즘이나 카테고리 선택을 넘기지 않는다. 요구사항이 명시되지 않았다는 사실만으로 작업을 멈추지 않고, 보존할 기능·기존 강도·확인한 제약을 근거로 설계 가정을 명시해 전환한다. 실제 필수 요구와 충돌하는 선택이나 미지원 구현은 채택하지 않으며, 배포 상대가 불명인 로컬 전환 결과를 외부 상호운용 성공으로 확대하지 않는다.

## 1. 기존 기능과 근거 확인

각 사용처의 `진입점 → 호출자/API → 키 출처 → 보호 대상 → 저장/전송 → 검증·복호화·실패 처리`를 연결한다. 실제 알고리즘·모드·키 크기/곡선·해시·컨텍스트와 상대 시스템을 기록한다. 인증서의 서명과 세션 키 설정처럼 한 프로토콜 안의 다른 기능도 분리한다. 호출 이름이나 의존성 선언만 발견했다면 아직 사용 확정이 아니다.

## 2. 전환 여부와 대체 기능 결정

| 확인된 기존 기능 | 전환 판정과 PQC 후보 계열 | 반드시 보존하거나 설계할 것 |
| --- | --- | --- |
| RSA-PSS/서명용 PKCS#1 v1.5, ECDSA, Ed25519/Ed448의 공개키 서명 | 양자 공격에 취약한 서명 경로를 PQC 서명으로 전환. ML-DSA·SLH-DSA, 허용된 KpqC 환경은 AIMer·HAETAE를 비교 | 누가 무엇을 인증하는지, 서명 대상 바이트·주석·컨텍스트, 공개키 신뢰·배포, 기존 서명 검증 정책 |
| RSA-OAEP 등으로 기존 데이터 키를 보호 | 키 보호 경로 전환. ML-KEM 또는 허용된 NTRU+·SMAUG-T의 공유 비밀에서 KDF로 키를 도출하고 AEAD로 기존 데이터 키를 보호 | KEM은 호출자가 정한 기존 키를 직접 암호화하지 않음. 새 봉투·키 식별·수신자 키 인증·실패 처리 필요 |
| RSA 공개키 암호화로 메시지를 보호 | KEM·KDF·AEAD를 결합한 메시지 암호화 구조로 재설계 | RSA 암호문과 새 암호문 형식 구별, 인증 범위와 평문 반환 시점. KEM API를 데이터 암호화 API처럼 치환하지 않음 |
| DH/ECDH/X25519 등으로 세션 키를 설정 | PQC KEM 기반 키 설정을 지원하는 프로토콜/라이브러리 경로로 전환 | 양쪽 역할·메시지 흐름·상대 인증·키 확인, 기존 순방향 비밀성·재전송 방지 등 요구 성질 |
| AES 등 대칭 암호, HMAC, 해시, 비밀번호 KDF | PQC 공개키 알고리즘으로 일괄 교체하지 않음. 강도·모드·키 출처를 점검해 유지 또는 별도 보강 | RSA/ECDH로 공급되는 공유키가 있으면 그 공급 경로를 전환. MAC을 공개키 서명으로 바꾸면 신뢰 모델도 달라짐 |
| 새 키와 형식에 의존하는 저장·복구·비밀번호 변경·파서 | 원시 알고리즘 교체와 함께 바꿀 연동 기능 | 새 키 생성·저장/복구, 구조체·길이·알고리즘 ID, 형식 버전, 기존 데이터 읽기와 오류 처리 |

RSA의 이름만 보고 KEM을 선택하지 않는다. **같은 RSA-3072라도 서명과 키 보호는 다른 전환안**이다. TLS·SSH·JWT·PKI 같은 표준 프로토콜은 합의된 PQC 프로파일·라이브러리 지원을 우선하며 독자 형식으로 기존 프로토콜과 호환된다고 주장하지 않는다. KEM의 인증·키 확인은 [NIST SP 800-227](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-227.pdf)을 참고한다.

전환 순서는 명시된 기한, 지금 수집한 암호문의 미래 복호화 위험, 서명 위조 피해, 키·상대 시스템의 교체 소요 시간을 근거로 정한다. 우선순위와 사용할 PQC 매개변수의 강도는 별도로 판단한다.

## 3. 공식 표로 후보를 좁히고 정확한 매개변수 결정

다음 값을 별도로 기록한다. **보존할 고전 보안 강도**는 기존 공개키 기능의 강도와 새 정책의 고전 강도 요구를 확인해 정한다. **명시된 최소 PQC 카테고리**는 적용 정책·프로토콜·고객/대회 요구에서 확인하며 없으면 미확인으로 둔다. **후보의 고전 강도·명세상 카테고리**는 공식 표에서 각각 읽는다. 기존 강도를 카테고리로 환산하는 중간 규칙은 두지 않는다.

### 기존 기능의 고전 강도 확인

[SP 800-57 Part 1 Rev. 5 §5.6.1·표 2](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf)의 RSA·ECC 강도를 사용한다. 아래 곡선은 해당 표의 ECC 범위에 속하는 예다. EdDSA는 [RFC 8032 §8.5](https://www.rfc-editor.org/rfc/rfc8032.html#section-8.5)의 명목 강도를 별도 근거로 사용한다.

| 공식 고전 강도 근거 | 기존 알고리즘·매개변수 예 | 고전 강도 |
| --- | --- | --- |
| SP 800-57 Rev. 5 표 2 | RSA-2048, P-224 | 112비트 |
| 같은 표 | RSA-3072, P-256 | 128비트 |
| 같은 표 | RSA-7680, P-384 | 192비트 |
| 같은 표 | RSA-15360, P-521 | 256비트 |
| RFC 8032 §8.5 | Ed25519 / Ed448 | 각각 128 / 224비트 |

표에 없는 키 크기·곡선은 공식 근거를 추가 확인하며 가까운 낮은 행으로 임의 반올림하지 않는다. ECC의 필드 크기만으로 Ed25519의 강도를 추정하지 않는다. 이 값은 양자 공격에 대한 보안 강도가 아니다.

### 신규 PQC 후보의 공식 강도 확인

[NIST IR 8547 최종본](https://csrc.nist.gov/pubs/ir/8547/final)(2026-10-27)의 **표 3은 서명, 표 5는 키 설정** 후보의 고전 강도와 PQC 카테고리를 함께 제공한다. 다음은 [해당 PDF의 표 3·5](https://nvlpubs.nist.gov/nistpubs/ir/2026/NIST.IR.8547.pdf)에서 Toolkit의 NIST 3개 계열만 정리한 것이다. 키·서명 크기와 상세 조건은 FIPS 203–205에서 확인한다.

| 기능·출처 | 매개변수 | 고전 강도 | PQC 카테고리 |
| --- | --- | --- | --- |
| 서명·표 3 | ML-DSA-44 | 128비트 | 2, 아래 RBG 조건 참조 |
| 서명·표 3 | ML-DSA-65 | 192비트 | 3 |
| 서명·표 3 | ML-DSA-87 | 256비트 | 5 |
| 서명·표 3 | SLH-DSA-SHA2/SHAKE-128s/f | 128비트 | 1 |
| 서명·표 3 | SLH-DSA-SHA2/SHAKE-192s/f | 192비트 | 3 |
| 서명·표 3 | SLH-DSA-SHA2/SHAKE-256s/f | 256비트 | 5 |
| 키 설정·표 5 | ML-KEM-512 | 128비트 | 1 |
| 키 설정·표 5 | ML-KEM-768 | 192비트 | 3 |
| 키 설정·표 5 | ML-KEM-1024 | 256비트 | 5 |

`SHA2/SHAKE`와 `s/f`는 여러 집합을 묶은 표기다. 선택 결과에는 `SLH-DSA-SHA2-128s`처럼 정확한 전체 이름을 적는다. IR 8547 표 3의 상태 기반 LMS/HSS·XMSS 계열은 이 Toolkit의 7개 알고리즘 범위 밖이다. KpqC 4개 계열은 이 NIST 표의 항목이 아니므로 아래의 별도 명세 확인 절차를 적용한다. [SP 800-57 Rev. 6](https://csrc.nist.gov/pubs/sp/800/57/pt1/r6/ipd)의 표 4·5도 참고할 수 있지만 확인일 현재 **Initial Public Draft**이며 최종본의 요구로 취급하지 않는다.

### 조건의 교집합으로 후보 선정

같은 기능의 후보에서 **공식 고전 강도 ≥ 보존할 고전 강도**를 만족하는 집합을 남긴다. 명시된 최소 PQC 카테고리가 있으면 **후보 카테고리 ≥ 해당 요구**도 별도로 적용한다. 이후 허용 표준·정확한 상대 프로파일·지원 구현·자원 제약을 확인한다. 필수 조건과 충돌하는 후보는 이유를 기록해 제외하고, 조건이 미확인이면 충족으로 표시하지 않는다.

기존 고전 강도를 낮추지 않는 것은 **Toolkit의 보존 목표**이며, 공식 표가 특정 기존 알고리즘에 한 집합을 의무화한다는 뜻은 아니다. 예를 들어 Ed25519의 128비트를 보존하고 별도 카테고리 요구가 없으면 ML-DSA-44와 SLH-DSA-128 계열 모두 강도 조건을 충족한다. 같은 대상에 최소 카테고리 3이 명시되면 ML-DSA-65/87과 SLH-DSA-192/256 계열만 남는다. Ed448의 224비트는 위 서명 표의 256비트 행부터 비교한다. 112비트 기능은 위 PQC 후보의 최저 고전 강도가 128비트이므로 상향 비교한다.

해시·KDF·키 엔트로피·인증의 약점은 별도로 확인한다. 취약한 기존 구성을 새 목표를 낮추는 근거로 쓰지 않는다. 다른 기능의 AES-256, 긴 보관 기간, 루트 키 여부만으로 서명의 카테고리를 자동 결정하지 않는다. 기밀 유지/서명 검증 기간·위조 피해·교체 소요 시간은 전환 우선순위와 추가 여유의 근거로 기록한다.

**남은 후보에서 구현에 사용할 한 집합을 정한다.** 정확한 프로파일 지정이 있으면 모든 필수 조건과 함께 충족하는지 확인한다. 지정이 없고 계열을 정했다면 다음 규칙을 적용하며, 다른 선택은 이유를 기록한다.

[NIST SP 800-57 Part 1 Rev. 5 원문](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-57pt1r5.pdf)은 최소 요구를 충족한 후보의 성능·메모리 비교를 허용한다. 같은 지침의 전환 권고는 목적에 적절한 강한 선택으로 재전환 비용을 줄이는 것과 과도한 크기의 성능 부담을 함께 고려한다. 지정된 Toolkit에 `docs/SELECTION_EVIDENCE.md`가 있으면 해당 발췌·절/쪽수를 참고할 수 있다. 최소 집합을 운영용 최종값으로 자동 확정하지 않고, 추가 보안 여유·보호 기간·교체 비용과 실제 제약을 함께 기록한다.

- **ML-DSA:** 강도·카테고리·지원 등 조건을 모두 통과한 집합 중 가장 작은 집합을 로컬 실험의 구현 시작점으로 정할 수 있다. 이는 Toolkit의 실험 순서이며 NIST의 일괄 권고나 운영용 최종 선정이 아니다. 최종 선정에는 더 높은 집합의 추가 여유·상대 요구와 비용을 비교한 근거를 남긴다.
- **ML-KEM:** 조건을 통과한 경우 NIST의 기본 권고인 768을 먼저 선택한다. 보존 강도 256비트 또는 최소 카테고리 4·5 요구가 있으면 1024만 남는다. 512는 강도·카테고리 조건도 통과하고 정확한 프로파일이나 확인한 자원 제약의 근거가 있을 때 선택한다. 기본 권고로 필수 조건을 무시하지 않는다.
- **SLH-DSA:** 표에서 남은 강도 계열 중 SHA2/SHAKE와 s/f까지 상대 프로파일·지원 구현·크기/지연 우선순위에 따라 정한다. 미측정 성능을 근거로 가장 빠르다고 단정하지 않는다.
- **KpqC:** 허용된 환경에서 고정한 공식 명세의 고전 강도·카테고리 주장과 적용 조건을 확인해 별도로 비교한다. 강도 근거가 부족하면 추가 조사로 남긴다. NIST 표에 없다는 이유만으로 구현 미지원이라고 표시하거나 NIST 매개변수와 숫자만으로 대응시키지 않는다. NIST FIPS 알고리즘이 필수인 경로의 대체 후보로는 취급하지 않는다.

명세 분류만으로 구현 강도를 보장하지 않는다. 예를 들어 [FIPS 204 §3.6.1](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.204.pdf)에 따라 ML-DSA-44의 카테고리 2를 유지하려면 키 생성 RBG의 보안 강도가 192비트 이상이어야 한다. 128비트 이상·192비트 미만의 승인된 RBG를 쓰면 주장 강도는 카테고리 1로 낮아진다. 선택한 라이브러리의 실제 키 생성 난수 경로·요구 강도를 확인하고, 미확인은 미검증으로 남긴다. 감소한 강도가 목표에 미달하면 그 구현을 채택하지 않는다.

미확인 운영 제약이 있어도 양쪽을 수정하는 로컬 실험처럼 적용 범위·가정이 명확하면 구현용 집합을 선정하고 시험한다. 목표 강도나 해당 집합의 지원 근거가 없거나 필수 조건이 충돌하면 이유를 명시해 선정 보류로 남긴다. **매개변수 선정과 실제 앱 검증은 다른 단계**이며, 측정 전이라는 이유만으로 구체 선택을 계속 미루거나 선택했다는 이유로 검증 완료라고 하지 않는다.

## 4. 실제 대체안 선택과 변경 범위

1. 동일 기능과 보존 목표를 충족하는 후보에서 명시된 표준·상대 프로파일·라이브러리/OS 지원을 확인한다. 필수 조건들의 교집합이 없으면 선정 보류로 기록하며 어느 한 조건을 임의로 무시하지 않는다. KpqC는 고정한 공식 명세의 강도 주장부터 대조하고 NIST FIPS와 혼동하지 않는다. 지원하지 않는 조합을 성공 후보로 표시하지 않는다.
2. NIST는 ML-DSA를 주요 서명 표준, SLH-DSA를 다른 기반의 대안으로 소개한다([공식 발표](https://www.nist.gov/news-events/news/2024/08/nist-releases-first-3-finalized-post-quantum-encryption-standards)). 일반 서명에서 ML-DSA를 먼저 시험할 수 있지만 검증기·명세·보안 가정 요구가 다르면 대안을 비교한다. [FIPS 203 §8](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.203.pdf)의 ML-KEM-768 기본 권고는 KEM 선택의 별도 근거다. 표에서 512가 강도 비교 후보라는 사실과 NIST의 768 권고를 구분한다.
3. 공개키·비밀키·암호문/서명 크기와 인코딩·헤더·서명 개수를 계산하고, 필요한 속도·처리량·메모리는 대상 환경에서 측정한다. 예산이 미확인이면 임의 합격선을 만들지 않고 미측정 항목을 충족으로 표시하지 않는다. 수정 가능한 기존 버퍼는 연동 변경 대상이며 변경 불가능한 상대 한도와 구별한다. 필수 강도/기능과 크기 한도가 충돌하면 형식·프로토콜 변경을 검토하며 목표를 몰래 낮추지 않는다.
4. 새 키 생성·배포·보호, 서명/암호문 버전, 기존 데이터 읽기, 키 회전·복구·폐기와 실패 처리를 전환안에 포함한다. 키 ID 일치만으로 신뢰를 인정하거나 기존 개인키/암호문을 이름만 바꿔 PQC로 취급하지 않는다.

## 5. 선정 결과와 검증

결과는 `기존 사용처·역할·키/해시 → 양자 취약성과 전환 이유 → 보존할 고전 강도·명시된 최소 PQC 카테고리 → 공식 표의 후보·제외 이유 → 선정 알고리즘·정확한 매개변수·공식 카테고리·선택 이유 → 함께 바꿀 경로 → 필요한 시험` 순서로 남긴다. 근거 문서의 버전·표 번호, 원시 키·서명/암호문 크기, 적용 범위·미확인 조건·재선정 조건을 함께 적는다. 서명 모드·컨텍스트 또는 KDF·AEAD 등 상세 프로파일의 미결 항목도 별도로 남긴다. 알고리즘·매개변수·카테고리 중 하나라도 미정이면 선정 완료로 표시하지 않는다. 명시된 최소 요구가 미확인인 것과 선정 집합의 공식 카테고리가 미정인 것은 구분한다. 전환·유지·연동 변경·추가 조사 판단과 앱 검증 상태를 구분한다.

보고서에서 선택을 재현할 수 있도록 대상 프로젝트의 지정된 근거 기록에 문서 상태·발행일·확인일·절/표·본문/PDF 쪽수·짧은 원문 발췌와 비공식 번역을 남긴다. Toolkit의 근거 문서는 읽기 전용 참고 자료이며 새 문제의 기록을 거기에 추가하지 않는다. 사례 문서는 해당 근거를 연결하고 공식 사실, 프로젝트의 해석·가정, 실제 측정 결과를 구분한다. 선정한 매개변수와 실제 키 표현·바이트 크기를 명시하고, 실험용 선정·운영용 선정·적용 검증의 상태를 별도로 남긴다.

정상·변조·잘못된 키·실패 시 출력/권한·기존 형식·다운그레이드와 키 관리 회귀를 대상 앱에서 확인한다. 키 설정은 공유 비밀 일치만으로 끝내지 않고 인증·키 확인·재전송·필요한 순방향 비밀성까지 검증한다. 원시 기능·공식 벡터·상호운용·앱 통합 상태는 별도로 기록한다. 새 조건을 발견하면 기존 기능과 보존 목표부터 대조하며, 선정 자체가 운영 배포 권한이나 PQC 적용 완료를 뜻하지는 않는다.
